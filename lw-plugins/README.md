# lw-plugins

Skills covering the **LW Plugins family** (LW LMS, LW Site Manager, Elállás for WooCommerce, LW Firewall). Use these when extending or building on top of these plugins.

The five **LW Firewall** skills are grounded on v1.5.4 and split by the surface you are working against: the early MU-plugin worker and its rate limits, the registration guard, password-reset flood protection, management/CLI/abilities, and — for a form the plugin does not cover — a custom-form adapter that documents where the reusable primitives stop.

## Skills

| Skill | Purpose |
|---|---|
| `lw-lms-backend-extend` | Backend extension contract for `lwplugins/lw-lms` (BETA — README explicitly says "not recommended for production use"), verified for v1.6.0 / PHP 8.2+. Headless LMS — courses / lessons / sections / progress / access control. v1.6.0 makes `lw_lms_has_course_access` the final logged-in paid-course decision after built-ins and adds `AccessRepository::revoke_by_source()` for integration-owned stored grants. Covers access/progress hooks and repositories, source/source-ID caveats, settings tabs, WooCommerce subscriptions/memberships, 11 custom capabilities, three DB tables, and optional Site Manager integration. Routes abilities, frontend, migration, and WP-CLI topics to sibling skills. |
| `lw-lms-wp-cli-operations` | Operational LW LMS WP-CLI commands added in v1.4.0, verified against v1.6.0 — `wp lw-lms course create\|list\|delete\|set-section`, `lesson create\|list\|assign`, `enroll`, `revoke`, `force-complete`. Covers argument resolution, repository/hook side effects, and CLI footguns. The v1.6.0 `revoke_by_source()` API is PHP-only: CLI `revoke` still changes the first active row regardless of source and exposes no source selector. **Not** the LearnDash migration command. |
| `lw-lms-rest-frontend` | Build a custom frontend against `lwplugins/lw-lms`'s headless `/wp-json/lms/v1` REST API (BETA, verified for v1.6.0). The route/schema catalog is unchanged; v1.6.0 server-side paid-access filters can now affect `access.has_access`, lessons, progress writes, attachments, and downloads. Since v1.4.0 single-course `content` is PUBLIC marketing/about content; only lesson content stays access-gated. Denied paid-course `access` can carry products, subscriptions, subscription variations, and WooCommerce Memberships plans. |
| `lw-lms-abilities` | Consumer / reviewer reference for the built-in `lw-lms/*` Abilities API surface registered by lw-lms v1.6.0 — `list-courses`, `get-course`, `get-progress`, `set-progress`, `get-options`. The v1.6.0 access changes added no ability. Covers the Site Manager bridge, standalone WP 6.9+ fallback, permissions, `input`-wrapped REST calls, and output schemas. |
| `lw-lms-learndash-migration` | Plan, run, or review the one-time WP-CLI LearnDash → LW LMS migration (`wp lw-lms migrate-learndash --dry-run --verbose`) in lw-lms v1.6.0; the v1.6.0 access changes did not alter its flow. Maps `sfwd-courses` / `sfwd-lessons` into `course` / `lesson` posts, writes reverse mappings, builds generated sections from `ld_course_steps`, and extracts video URLs. Rerunnable but not a sync; it does not migrate quizzes, certificates, groups, assignments, user progress, enrollments, or drip rules. |
| `lw-site-manager-overview` | Reference for `lwplugins/lw-site-manager` — a WP 6.9+ Abilities-API-native exposure layer that registers 120+ machine-callable abilities under `site-manager/*` for AI agents (Claude, ChatGPT, MCP clients) to discover and invoke. Calling pattern via `/wp-json/wp-abilities/v1/abilities/{namespace}/{ability}/run` with Application Password Basic auth. **Not** MainWP — different surface and security model (per-ability cap-checks). |
| `lw-site-manager-extend-abilities` | Add custom abilities to LW Site Manager via two action hooks (`lw_site_manager_register_categories`, `lw_site_manager_register_abilities` — second receives the central `PermissionManager` instance). Critical pattern — extend `AbstractAbilitiesRegistrar` to inherit the meta builders (`readOnlyMeta` / `writeMeta` / `destructiveMeta`) and schema builders (`paginationSchema` / `orderingSchema` / `idSchema` / `listOutputSchema` / etc.). |
| `lw-elallas-integration` | Integrate with or extend **Elállás for WooCommerce** (`elallas-for-woo`, verified v1.0.12) — the EU/HU right-of-withdrawal (elállás) case-management plugin. An LW-family plugin (namespace `LightweightPlugins\Elallas`, `wp_lw_elallas_*` tables) you integrate by CONSUMING hooks, never editing. Covers the eligibility/deadline/B2B/order-number filters (`elallas_is_order_eligible`, `elallas_deadline_days`, `elallas_is_order_b2b`, `elallas_delivery_date`, and the new `elallas_resolve_order_number` for custom/sequential order numbers — never `absint()` the display value), the case-lifecycle actions (`elallas_case_created` / `_confirmed`, the now **4-arg** `elallas_case_status_changed` with the customer-visible note, `elallas_invoicing_case_created`), `elallas_pdf_html` and `elallas_boot`, the `CaseStatus` lifecycle, product/category/tag withdrawal exceptions (`_lw_elallas_excluded` → `eligibility_flag = 'excepted'`), the runtime WPML/Polylang string + page-ID translation paths (and the intentionally narrow `wpml-config.xml` scope), PII-scrubbed WooCommerce logging, the 4 custom tables + read-only order meta, and the `elallas/*` LW Site Manager abilities. HPOS-safe; detect with `defined('ELALLAS_FOR_WOO_VERSION')`. |
| `lw-firewall-rate-limit-worker` | Make your plugin compatible with **LW Firewall** (`lw-firewall`, verified v1.5.4) and its MU-plugin worker that runs on `muplugins_loaded` priority 1. Covers the fixed worker check order (kill switch → `enabled` → server/localhost skip → `ip_whitelist` → `ip_blacklist` → geo → auto-ban → 404 flood → bot UA → endpoint detection → rate limit), which request types the worker actually detects (`cron`/`xmlrpc`/`login`/`rest`/`filter` — bare `/wp-json`, `?rest_route=`, `admin-ajax.php` and arbitrary pretty URLs are NOT covered), the separate logged-in REST/filter bucket (cookie **shape** only, 10× headroom by default — never a cryptographic check and never a full exemption), narrow `filter_params` substring rules with per-prefix limits, endpoint-local self-protection via `RateLimiter::is_allowed_key()` + `AutoBanner` + `lw_firewall_resolve_storage()`, the `IpDetector::get_ip()` Cloudflare-range trust model, whitelist/blacklist CIDR handling, worker lifecycle (install/remove/version-mismatch bail), response codes, and the `LW_FIREWALL_*` wp-config overrides. Names the verified 1.5.4 limits a companion must design around: `Options::get_all()` does **not** apply the constants the worker reads, a `ban_<ip>` written by the registration/reset producers is enforced only when `auto_ban_enabled` or `login_limit_enabled` is on, and `AutoBanner::unban()` does not clear the `<reason>_<ip>` endpoint counters. |
| `lw-firewall-registration-guard` | Wire a **custom registration form or signup REST endpoint** into LW Firewall's spam protection (verified v1.5.4). The plugin auto-protects only the default WP `register_form`/`registration_errors` pair, and only when the worker is healthy, `enabled` and `register_protect_enabled` are true, and `users_can_register` is on — custom, AJAX, headless, Woo/CRM/LMS signups must opt in. Covers the proof-of-render token (`lw_fw_reg_token`) + honeypot (`lw_fw_url`), the public surface `RegisterGuard::render_fields()` / `RegisterGuard::validate( WP_Error )` / `RegisterToken::issue()` / `RegisterToken::verify( $token, $min, $max, $storage, $scope )` / `RegisterTracker::record_reject()`, atomic single-use replay protection, generic error messaging (never leak which check failed), and the reject-count auto-ban shared with the worker store. States the token's real security meaning — an anti-automation signal, not a WordPress nonce and not proof a human filled the form, so keep your own CSRF and capability checks — and flags the 1.5.4 caveat that a registration-only default config can record a `register_spam` ban the worker never enforces. `references/registration-and-rest-integration.md` carries the transport-independent validator, REST route shape, bootstrap response and required tests. |
| `lw-firewall-management-abilities` | Automate or audit **LW Firewall** management (verified v1.5.4) across its surfaces — WP-CLI (`wp lw-firewall status\|config\|config-items\|ip\|worker`, plus the `ban`, `bots`, `geo`, `logs`, `alerts` and `reset` command groups), LW Site Manager abilities (`lw-firewall/get-options`, `get-log`, `list-blocked`, `block-ip`, `unblock-ip`, all behind the manager's `can_manage_options` callback rather than a public `__return_true`), and admin import/export. Covers the single-option model (`Options::get_all()` / `save()` merge-with-defaults, list-typed keys), the load-bearing asymmetry that `LW_FIREWALL_*` constants win only on single-value `Options::get()` reads while `get_all()` — used by the worker, the runtime hook bootstrap, the geo `.htaccess` sync and status — ignores them, why abilities only touch the **manual** `ip_blacklist` (auto-bans live in the storage backend), the capped 100-entry `lw_firewall_log`, administrator-alert baselines, password-reset settings, MU-worker status/reinstall, and safe config migration. |
| `lw-firewall-password-reset-protection` | Configure, integrate or audit LW Firewall's **password-reset flood protection** (verified v1.5.4) — the `lostpassword_post` / `lostpassword_form` / `allow_password_reset` guard that covers core `wp-login.php` and WooCommerce alike. Covers the three counters and their real evaluation order (per-IP → global → target account), the proof token + honeypot on the reset form, `ResetLimiter` verdicts and `ResetPenalty` behavior (why a `global` / `user` refusal must not ban the requester), the opt-in `reset_block_admins` hardening and its `administrator`-role-only scope, reset alerts, reset auto-ban, and the `reset_*` options / `wp lw-firewall reset` operations. Names the verified 1.5.4 constraint a companion form must design around: the documented “reset emails per hour” global cap is consumed by **refused** requests too, so a distributed flood can exhaust it for every account. |
| `lw-firewall-custom-form-adapter` | Design or audit an LW Firewall adapter for a **custom public form** that is neither the built-in registration nor the lost-password form — contact, lead, quote, application, custom signup, AJAX or REST (verified v1.5.4). Starts from the honest boundary: 1.5.4 exposes **no** generic “protect this form” API, so the skill states what may be reused (`RegisterToken`, `RateLimiter::is_allowed_key()`, `lw_firewall_resolve_storage()`) and where those primitives stop — the token signs only a second-precision timestamp (identical within the same second, shared-cache unsafe) and is not cryptographically bound to a form, `$scope` only namespaces the replay key, and the limiter lets you override the count but not the window. Covers a developer-owned replay scope, strict honeypot **presence and emptiness**, render-neutral token issue for REST/headless, `private, no-store` on anonymous token responses, an explicit fail-open/fail-closed policy, and the layers the adapter must not replace (nonces, capabilities, schema validation, upload policy, a real bot challenge). Forbids logging an arbitrary contact-form failure as a `register_spam` event or advertising the adapter as a built-in LW feature; `references/generic-form-guard-proposal.md` specifies the upstream contract such a feature would need. |
